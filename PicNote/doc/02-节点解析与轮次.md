# 竹节笔记 / Bambootes · 02 节点解析与轮次

本文规定解析状态、批次打包、流式协议与本地提交。上下文与预算见 [03-上下文与记忆.md](03-上下文与记忆.md)，界面见 [04-界面升级.md](04-界面升级.md)，表结构与迁移见 [05-存储、配置与迁移.md](05-存储、配置与迁移.md)。

## 1. 状态与字段

`node_parse` 与正文节点 1:1，随节点删除级联清理：

| 字段 | 说明 |
| --- | --- |
| `node_id` | 主键，外键指向 `nodes.id` |
| `parsed_markdown` | 解析文字，模型产出或用户修正 |
| `parsed_hash` | 产出这段文字时的 `content_hash`；用户修正不改该值 |
| `state` | 落库只取 `pending / parsed / failed` |
| `origin` | `model` 或 `user` |
| `detail` | 是否“精细识别”（公式、代码、表格），进入 `content_hash` |
| `summary` | 摘要，≤160 token，用于分段记忆 |
| `tags` | 逗号分隔的标签 |
| `updated_at` | 最近一次写入时间 |

`content_hash` 覆盖规范化后的 `body_markdown`、图片 `hash` 的有序列表与 `detail`，不含 `sort_key`。纯排序、纯拖动不改变任何节点状态。

| 状态 | 含义 | 界面 |
| --- | --- | --- |
| `pending` | 有图片且从未成功解析 | “待解析” |
| `parsing` | 已进入活跃轮次、尚未提交 | 进度点 + “解析中”或“本轮排队” |
| `parsed` | `parsed_hash == content_hash` | “已解析” |
| `stale` | 已解析但内容已变 | “待更新” |
| `failed` | 上次以可重试错误结束 | 红色“失败 · 重试” |

`parsing` 只存在于执行器内存，不落库。进程退出后不会留下卡死状态，启动时不需要修复 `parsing`。`stale` 由 `state = parsed` 且 `parsed_hash != content_hash` 推导，同样不单独落库。

状态迁移：

| 操作 | 结果 |
| --- | --- |
| 导入图片生成新节点 | `pending` |
| 换图、加图、删图、改备注、切换 `detail` | 已有文字 → `stale`；从未解析 → `pending` |
| 用户修正解析文字 | 保持当前状态，`origin = user`，`parsed_hash` 不变 |
| 提交成功 | `parsed`，`parsed_hash = content_hash` |
| 网络或服务端可重试错误 | `failed`，保留旧文字 |
| 点“重试” | 重置为 `pending`，进入下一次提交 |
| 无图片的正文节点 | 不建 `node_parse`，不出现在解析界面 |

## 2. 选谁与分批

一次提交纳入当前文档全部 `pending` 与 `stale` 节点，按链序排列。`failed` 不自动纳入，需用户点“重试”。底部按钮的 `N` 即为纳入数量。

- 每批最多 6 张图，单节点超过 6 张图时独立成批，并按模型接口硬上限重新校验；仍放不下时提示用户拆分节点，不截断内容。
- 批次串行：一批提交完成后才发下一批。某批失败停止后续批次，未提交节点保持原状态。
- 图片顺序由请求适配器按节点内 `sort_index` 生成映射，不复用界面上的“第几张”。

```json
{
  "turn_id": "t7",
  "protocol_version": 1,
  "batch_index": 1,
  "mode": "parse",
  "preferences": {"language": "zh-CN", "structure": "outline", "terms": "preserve", "length": "normal"},
  "brief": {"node_id": "n02", "text": "观看 Transformer 讲解视频，记录注意力公式与多头的作用。"},
  "heading_index": [{"node_id": "n09", "level": 2, "title": "多头注意力"}],
  "ordered_nodes": [
    {"node_id": "n05", "content_hash": "h05", "user_text": "比较单头和多头", "detail": false, "image_ids": ["i05a", "i05b"]}
  ],
  "images": [{"image_id": "i05a", "node_id": "n05"}, {"image_id": "i05b", "node_id": "n05"}],
  "context": [{"kind": "neighbor", "source_ids": ["n04"], "text": "Q/K/V 由独立投影获得。"}]
}
```

`brief` 取引言节点全文，未填写则省略。`heading_index` 只含当前章节标题与序号，供模型理解位置，模型不得引用未列出的节点 ID。`context` 的组成与预算见 03。

## 3. 流式协议

网络 SSE 先由适配器解码，再累积文本增量，按换行切分为完整 NDJSON 行，最后校验业务事件。网络帧边界不等于 JSON 行边界；末尾未闭合的行不视为成功。

| `kind` | 关键字段 | 处理 |
| --- | --- | --- |
| `stage` | `stage` | `reading / extracting / writing`，只更新遮罩文案 |
| `node` | `node_id, markdown, summary, tags` | 校验后立即本地提交该节点 |
| `done` | `node_ids` | 核对本批覆盖范围，缺漏节点保持原状态并提示 |
| `error` | `code, message, retryable` | 记录错误，`retryable` 决定节点是 `failed` 还是保持 `pending` |

```json
{"kind":"stage","stage":"extracting"}
{"kind":"node","node_id":"n05","markdown":"多头注意力把 Q/K/V 各自投影 h 次，并行计算后拼接。","summary":"多头并行投影后拼接","tags":["Attention"]}
{"kind":"done","node_ids":["n05"]}
```

单行 JSON 解析失败保留原文并计数，连续 3 行失败终止该批。未知 `node_id`、不属于本文档、节点无图片、`markdown` 为空的行直接丢弃并计入该节点错误。不存在提交分组，一条 `node` 行即一个完整结果。

## 4. 本地提交

`DocumentRepository.commitParse(documentId, turnId, nodeId, contentHash, markdown, summary, tags)` 与现有写操作共用主 `Mutex` 与 `NonCancellable` 事务区间：

1. 事务前重新计算该节点 `content_hash`，与请求快照不一致则放弃该行，`turn_item.error = content_changed`。
2. Room 事务内校验文档、节点仍存在且节点类型为 `body` 且至少一张图片。
3. 已存在 `node_parse` 且 `origin = user` 且 `parsed_hash == content_hash` 时不覆盖，只更新 `summary / tags`。
4. 写入 `parsed_markdown / parsed_hash / state = parsed / origin = model`，`turn_item.committed = 1`。
5. 删除覆盖该节点的 `memory_segments`（原子级失效，按需重建），`touchDocument`。
6. 事务提交后写 `doc.md` 镜像，失败沿用现有 `Saved.mirrorFailed` 提示与重试入口。

`turn_items` 以 `(turn_id, node_id)` 为主键，重复行直接跳过，保证重放不重复写入。提交不修改 `sort_key`、节点类型与其它节点内容。

## 5. 轮次

| 字段 | 值 |
| --- | --- |
| `mode` | `parse`（提交待解析节点）、`retry`（单节点重试或重新解析） |
| `status` | `running / finished / interrupted / failed` |
| 派生 | `batch_count`、`committed_count`、`node_total`、`created_at`、`finished_at`、`error` |

`running` 只允许一个。执行器独立于页面生命周期持有 Job、Call 与互斥锁，切换页面、切换文档、收起遮罩都不中断。启动时把遗留 `running` 置 `interrupted`；`turn_items` 中已提交的节点保持 `parsed`，其余节点本来就是 `pending` 或 `stale`，无需回退操作。

原文留档：

```text
filesDir/documents/<id>/parse/turns/<turn_id>.ndjson
filesDir/documents/<id>/parse/turns/<turn_id>/input-<batch_index>.json
```

NDJSON 记录实际返回行与本地提交结论；输入快照记录实际发送的节点 ID、hash、图片引用与压缩策略。两者都不含密钥、鉴权头与图片 base64。

## 6. 取消、失败与恢复

| 场景 | 处理 |
| --- | --- |
| 收起遮罩、切换 Tab 或文档 | 任务继续，顶部显示进度入口 |
| 用户确认取消 | `Call.cancel()` + Job 取消，结构化等待当前事务结束，`turn` 置 `interrupted`，已提交保留 |
| 网络断开 | 停止后续批次，提示“已保存 N 个，剩余 M 个待解析”；不重发已提交节点 |
| 进程退出 | `turn` 置 `interrupted`；已提交节点仍为 `parsed` |
| 重复提交 | 底部按钮禁用，执行器校验活跃轮次，写操作校验 `busy` |
| 单节点连续失败 2 次 | 置 `failed`，只统计可归因到该节点的错误，取消与未处理的排队节点不计 |
| 本地存储失败 | 不标记已解析，提示存储问题，恢复后重试未提交节点 |
| 服务端报超窗口 | 拆小当前批次重发未提交节点，不重发已提交节点 |

取消顺序固定为：置取消标记、取消 Call、等待当前事务、清理内存候选、释放互斥。不引入 generation 或 revision 状态；竞态由 Job 取消与事务内二次校验覆盖。

## 7. 用户修正与重新解析

- 编辑页可修改 `parsed_markdown`，保存后 `origin = user`，状态与 `parsed_hash` 不变，相关分段记忆失效，镜像刷新。修正不触发识图，不改历史轮次。
- “重新解析”对该节点单独发起 `mode = retry` 轮次，成功后替换文字并恢复 `origin = model`；失败保留原文字。
- 修改备注、换图或切换 `detail` 后节点为 `stale`，旧文字继续显示并标注“待更新”，直到新结果提交。

## 8. 验收

1. 提交 3 个节点、第 2 个接口报错：第 1 个为 `parsed`，第 2 个 `failed`，第 3 个保持 `pending`。
2. 取消后重进应用，已提交节点仍为 `parsed`，其余 `pending`，不存在 `parsing` 残留。
3. 同一 `turn_id` 重放不产生重复写入，`doc.md` 与文档页内容一致。
4. 修改图片后节点显示“待更新”，再次提交只重传该节点。
5. 用户修正文字后再提交其它节点，修正内容不被覆盖。
6. 只调整顺序不改任何内容，提交数量为 0，也不产生轮次。
