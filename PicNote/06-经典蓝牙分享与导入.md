# 经典蓝牙分享与导入

一台手机从竹节笔记选择一篇文档，另一台手机打开「蓝牙接收」。发送端把文档及其图片打成一个按文档标题命名的 `.zip`，通过经典蓝牙传给接收端。接收方确认一次，收完后自动导入为独立、可编辑的本地文档。

界面审阅可按发送端、接收端的顺序查看。[01-分享入口与扫描.png](原型图/蓝牙分享/01-分享入口与扫描.png) · [02-蓝牙接收与导入.png](原型图/蓝牙分享/02-蓝牙接收与导入.png)

## 两台手机上的操作

| 入口 | 点击后的行为 |
| --- | --- |
| 首页右上角「更多 → 蓝牙分享」 | 分享当前 `document.id`，节点和文档两个 Tab 均可用。菜单顺序为「合并」（仅节点 Tab）、蓝牙分享、完整导出、网页导出、复制文档、删除文档。 |
| `navMenu` 文档行「⋯ → 蓝牙分享」 | 分享被点行的 `item.id`，即使正在阅读另一篇文档也无需切换。蓝牙分享排在完整导出之前。 |
| `navMenu` 标题栏「＋ 新建」左侧的蓝牙接收图标 | 关闭抽屉并进入「蓝牙接收」，空文档列表也可使用。它与 `CreateDocumentButton` 垂直居中、外观等高，跟随系统字体缩放，两者均保留至少 48dp 点击区域。无障碍名称为「蓝牙接收」。 |

两个分享入口都打开「蓝牙分享」全屏页。返回恢复原首页 Tab 和阅读位置。沿用 `MainActivity`、`PicNoteApp` 的 Navigation 3 导航与 `SecondaryPageScaffold`。横屏左列占 30%，放返回、标题和主要操作，右列滚动显示设备或文件详情。现有「完整导出」「网页导出」继续走系统分享面板。

### 接收方先打开「蓝牙接收」

1. 页面突出显示本机蓝牙名称，例如「小林的手机」。等待接收时，「请让对方在『蓝牙分享』的设备列表中选择『小林的手机』」位于页面底部，距系统安全区底边 32dp。名称缺失时引导用户到系统蓝牙设置查看或设置名称。接收页在前台时保持屏幕常亮，离开页面后恢复原有策略。
2. 按需申请附近设备权限、请求系统开启蓝牙，开始监听竹节笔记服务，并通过系统弹窗申请限时可发现。系统同意后，圆环从整圈起按实际获准时长逐步缩短，圆心显示「等待接收」，下一行显示剩余分秒。最后 15 秒使用警示色。可发现时间耗尽或申请被拒绝后，圆心显示「重试」，点击再次请求系统允许附近设备发现。监听已就绪时，已配对的发送方仍可尝试连接。
3. 收到请求后，显示对方设备名、完整文件名、文件大小，提供「拒绝」和「接收并导入」。若对方撤回请求，关闭失效的确认框并恢复监听；拒绝后也恢复监听。点「接收并导入」才开始写文件，同一时刻只接收一份。
4. 传输时显示字节进度和取消操作。收完后切换为「正在导入」。成功时显示文档原题及「打开文档」，点击才切换到新文档；直接返回保留原来阅读的位置。接收成功后结束本次监听。若 Room 已提交而 Markdown 镜像写入失败，接收页同时提示镜像更新失败，已导入的文档仍可打开。

### 发送方打开「蓝牙分享」

1. 立即显示目标文档和「正在打包」。使用点击时确定的文档 ID 生成一致快照，文件就绪后展示实际文件名、大小。文件缺失、空间不足或文档已删除时停在此页显示原因。
2. 蓝牙就绪后显示「已配对设备」与「附近设备」，发起一轮经典蓝牙发现，按设备去重；一轮结束可「重新扫描」。空结果提示对方打开「蓝牙接收」并允许发现。附近列表中的名称仅代表系统发现的设备，能否接收由应用连接握手确认。
3. 点选接收页显示的设备名后停止扫描。已配对设备直接连接；首次使用时，发送端显示「正在配对」，由 Android 提示两台手机确认。若系统已在配对，就等待当前配对结果。目标设备配对成功后自动继续连接并发送文件摘要，无需重新选择设备。此时显示「等待对方接收」，只有接收方点「接收并导入」才开始传送文件内容。字节全部发出后显示「等待对方导入」。
4. 收到对端导入成功回执才显示「对方已导入」。对方拒绝、配对取消、对端未打开接收或版本不兼容时说明原因，允许重新选择设备。字节全部发出后，发送方可「停止等待」并在接收手机查看结果，对方可能已经完成导入。发送完后丢失回执时提示先在接收手机上核对结果。需要重发时由用户主动重新选择设备，以免生成重复文档。

## 文件名与文档包

分享文件名复用 `DocumentRepository.exportFileName(title, "zip")`。例如「杭州 / 周末」生成 `杭州-周末.zip`。中文标题、非法字符替换、保留名和 UTF-8 字节截断沿用现有规则。临时文件按会话目录隔离，同名文档可各自保留原文件名。接收后的文档标题取包内原题。

| ZIP 条目 | 内容 |
| --- | --- |
| `manifest.json` | UTF-8 编码，标记 PicNote 包类型和 `formatVersion = 1`，保存文档原题、有序节点、每个节点内有序的图片引用。 |
| `media/<包内素材名>.webp` | 直接写入本地已保存的 WebP 字节。每个引用的 `entry` 指向包内条目，`fileName` 保留文档中使用的素材名，并记录宽高、原图去重 hash 和 WebP 字节 SHA-256。同字节的素材在 ZIP 中只写一份，导入后按各自的合法素材名还原。 |

蓝牙导入以清单识别可编辑文档包。现有 `exportFull` 生成的 ZIP 只包含 Markdown 和图片，缺少恢复节点类型与边界所需的清单。收到这种包时提示「请在发送手机选择蓝牙分享」。

按现有 `DocumentContent` 顺序保存 `kind`、`title`、`bodyMarkdown` 与图片顺序。保留固定前两项 `title`、`introduction`，包括空引言，支持 `chapter`、`body`、`code`。旧版文档已有的额外 `introduction` 保留原类型和位置。代码块原样保留围栏、语言、描述与缩进。文档内使用 `media/<素材名>.webp` 的相对链接在接收端继续指向同一素材。设备专属的 `sourceUri`、相册快照和本地绝对路径不进入包。Markdown 镜像在导入后由节点重新生成。

复用项目已有的 `java.util.zip`。首版对含正文的 `manifest.json` 采用 **DEFLATE 5 级**，兼顾包大小与打包时间。已压缩的 WebP 条目使用 `STORED`：在锁内复制引用素材到会话快照时，同时统计长度、CRC-32 和 WebP 摘要，随后释放锁并按原样写入 ZIP。[ZipOutputStream](https://developer.android.com/reference/java/util/zip/ZipOutputStream)

用仓库内置中文教程素材对照，同一份 677 字节的 `document.json` 用 5 级和 9 级 DEFLATE 都得到 513 字节；10,920 字节的 `launcher.webp` 两档都得到 10,925 字节。以上仅计条目数据，不含 ZIP 头。这个样本支持采用中档压缩文字、直接存放 WebP；其他文档的收益随图文比例而变。

发送端边写 ZIP 边计算整包 SHA-256，归档关闭后取最终摘要和实际字节数。接收端边写临时文件边校验，收全后解包、导入。开发验收时选一篇以文字为主的笔记和一篇多图笔记，在同一对手机上分别记录打包时间、包大小、蓝牙传输时间和导入时间，以点分享至对端导入的总耗时评估档位。

## 蓝牙连接与会话

- `PicNote` 的最低版本是 Android 12。发送按需请求 `BLUETOOTH_SCAN` 和 `BLUETOOTH_CONNECT`，接收按需请求 `BLUETOOTH_CONNECT` 和 `BLUETOOTH_ADVERTISE`。扫描仅用于选择设备，声明 `neverForLocation`。拒绝时在当前页提供重新授权或前往设置的入口；设备不支持经典蓝牙时说明原因。开启蓝牙与允许发现均使用系统确认流程。[Android 蓝牙权限](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions) · [Android 蓝牙设备发现](https://developer.android.com/develop/connectivity/bluetooth/find-bluetooth-devices)
- 采用安全 RFCOMM 双向连接。两端使用同一个固定、竹节笔记专用的服务 UUID，接收端调用 `listenUsingRfcommWithServiceRecord`，发送端调用 `createRfcommSocketToServiceRecord`。扫描不能证明对端运行竹节笔记，服务 UUID 用于路由，协议标识与版本用于识别兼容客户端，系统配对和用户同意决定本次传输。[Android 蓝牙设备连接](https://developer.android.com/develop/connectivity/bluetooth/connect-bluetooth-devices)
- 每条连接承载一个文件。双方先交换协议标识和版本，再发送文件名、字节长度、整包 SHA-256。控制消息带长度前缀并限制长度。接收方回复接受后，发送方按约定字节数写入文件体。接收方校验并提交后回传「导入成功」。发送端在写正文的同时监听回执，接收端写盘失败时可以立即回报具体原因。为兼容先写完正文才读回执的旧发送端，接收端会在失败后短暂排空剩余正文，超时则关闭连接。旧发送端可能只看到断连。网络读写与打包在后台线程执行，不持有仓库写锁等待对方操作。
- 每轮扫描、监听或传输只保留一个活动任务。重新扫描前结束上一轮并注销发现回调，退出或取消时关闭 socket 解除阻塞，等待任务结束再清理临时文件。配置重建复用同一会话；系统配对、授权与限时可发现弹窗返回后续接原步骤。主动离页或应用真正进入后台时结束前台传输；写入中的会话先确认取消，Room 已开始提交时等待提交结果。超时、蓝牙关闭、空间不足或断连都给出对应状态。

## 导入与旧数据

1. 接收内容先写入本次会话的私有暂存目录，使用本地生成的路径。按声明长度接收并核对整包 SHA-256。打开 ZIP 后校验包标记、版本、节点约束、素材引用、图片有效性与摘要。拒绝越界路径、重复条目、未知节点类型及缺失素材。为压缩包大小、解压总量、条目数、解码内存设置上限，读取时按实际字节累计执行。
2. 为文档、节点和图片生成本机新 ID，按清单顺序重建 `sortKey` 和 `sortIndex`。`NodeImageEntity.hash` 保存发送端原有去重值，`sourceUri` 置空，跳过 `SourceImageEntity`。即使同名或收到内置教程也新建普通文档，已有文档和教程 ID 保留。
3. 素材校验结束后，在 `DocumentRepository` 的互斥锁内将暂存素材移至新文档目录，再以单个 Room 事务写入文档、节点与图片。事务失败则撤销新目录；进程中断后由 `PicNoteCleaner` 清理无文档记录的目录与陈旧暂存。提交成功即完成导入，镜像写入失败复用现有的重建流程。已提交的导入结果在回执丢失时仍有效。
4. 归档版本独立于 Room 版本，首版可沿用现有表结构、本地文件布局与配置。遇到高版本包时提示更新应用。旧版竹节笔记缺少接收服务，发送页引导对方更新并打开「蓝牙接收」。

`formatVersion = 1` 的 ZIP 文件和解压后条目总量各限 256 MiB，清单限 4 MiB，单张 WebP 限 64 MiB、解码像素缓冲限 128 MiB。一篇文档最多包含 4096 个节点、1024 个独立图片条目和 8192 次图片引用，单个节点的标题与正文合计限 1 MiB。收发两端采用相同上限。

## 双机验收

| 场景 | 应看到的结果 |
| --- | --- |
| 正在阅读 A，从抽屉 B 的行菜单分享 | 发出 B 的标题、文件及素材，返回后仍在 A。顶栏分享发出 A。 |
| 接收端文档为空，两机此前没有配对 | 可从新建旁的图标进入。发送端选中对方后，两台手机按系统提示完成配对，同一次分享继续到「接收并导入」；再次分享直接进入连接。 |
| 目标设备正在配对，或任一方取消配对 | 正在配对时沿用这次系统请求。取消或超时后回到设备选择，重新点选即可重试，原会话不会发送文件。 |
| 一篇包含空引言、章节、多图正文及带语言代码块的文档 | 收到后可编辑；节点、图片顺序、代码空白与原文一致。同名文档各自可独立编辑、删除。 |
| 可发现到期、未授权、拒收、轮换屏幕、传输中取消 | 可恢复授权或重新扫描，旋转不重复打包或导入，取消后没有半篇文档。 |
| 旧版对端、截断文件、摘要错误、缺图、空间不足 | 对应页面指出失败环节，原文档可继续使用，未提交的内容不会出现在列表。 |
| 两端传完文件，接收已提交，但发送端丢失回执 | 接收端仍可打开文档，发送端显示结果未确认，用户可先核对再决定是否重发。 |
