# AGit Git 操作流程

## 状态判断

以当前本地分支及其在 `origin` 上的目标分支为比较对象。默认分支以仓库实际配置为准，不写死 `main` 或 `master`。

- `dirty`：存在未提交的工作区、暂存区或未跟踪文件变化，遵循 Git 的忽略规则。
- `ahead`：本地独有的提交数量。
- `behind`：目标远端分支独有的提交数量。
- 外部编辑尚未结束时，即使仓库目录暂时没有变化，也不能当作可以更新文件的干净状态。

以下状态只在本次 fetch 成功、目标分支存在且提交关系可以确认时成立：

| 本地状态 | 提交关系 | 更新与推送行为 |
| --- | --- | --- |
| 无文件修改 | `ahead = 0`，`behind = 0` | 已同步，无需更新或推送 |
| 有文件修改 | `ahead = 0`，`behind = 0` | 允许 commit；push 前重新 fetch |
| 无文件修改 | `ahead > 0`，`behind = 0` | 允许普通 push |
| 有文件修改 | `ahead > 0`，`behind = 0` | 已选文件完成 commit 后允许推送 commit；未选文件保留在本地，不随 push 上传 |
| 无文件修改 | `ahead = 0`，`behind > 0` | “更新”自动 fast-forward；push 检查只提示远端有更新并阻止推送 |
| 有文件修改 | `ahead = 0`，`behind > 0` | 保留文件、不自动更新；先 commit，后续 push 检查会阻止向原分支推送 |
| 任意文件状态 | `ahead > 0`，`behind > 0` | 提交历史分叉；禁止向原目标分支 push，用户可在 commit 完成后选择新建分支推送 |

即使本地与远端修改的是不同文件，只要满足上述双向修改条件，第一版也不尝试合并。

## Clone

1. 首次使用先填写 Token 名称和 Token 创建一级分组。点击抽屉 `+` 时先选择已有分组或新建分组，再输入 GitHub HTTPS 仓库地址，使用该分组的 Token 认证。
2. 选择完整 clone、depth 或无Git。depth 默认 10，可用居中的左右箭头调整，最小为 1；只有该模式设置 JGit 的 `setDepth`。无Git 使用 GitHub ZIP 归档接口下载默认分支，不通过 clone 后删除 `.git` 实现。
3. 在临时目录完成下载、检出或解压后，将 `content/` 原子移动到 `filesDir/shared/<projectId>/`，成功登记后才显示为可用项目。记录模式和初始 depth；旧项目缺少模式时按完整 clone 处理。
4. Git 项目保留所属 Token 分组、`origin`、实际分支及远端跟踪关系。后续 fetch 不重新设置 depth，不主动截断已有历史；浅仓库无法确认共同祖先时阻止更新和推送，并提示历史深度不足。
5. 无Git 项目保留所属分组及源地址，仅支持查看；文件读取共用项目锁，但不打开 JGit 仓库，数据层同时拒绝编辑与 Git 写操作。
6. 失败或取消时等待任务退出后删除未完成目录，保留错误原因，重试不得覆盖已有项目目录。

## Commit

1. 重新扫描修改，允许逐文件勾选将纳入提交的内容，并填写提交说明。不做按代码行拆分提交；新增、修改和删除均按文件处理，重命名需保持原路径和新路径操作完整。
2. 首次提交前配置有效作者邮箱，姓名选填；姓名留空时取邮箱 `@` 前的部分作为 Git 作者名。Token 不自动充当提交身份。
3. 仅对选中的文件创建普通 commit，未选文件保持原状；已有暂存内容也必须纳入可见选择，不能隐式夹带进提交。提交成功后更新状态，commit 不隐式 push。
4. 没有待提交内容时不创建空提交；失败时保留文件和用户填写的提交说明。

## 更新

1. 执行 `fetch origin`，刷新远端跟踪引用。
2. 重新读取当前分支、文件修改状态及目标分支，计算 `ahead` 与 `behind`。
3. 按状态表处理：只在本地无修改且仅落后时自动快进；文件变化、未结束的外部编辑或历史分叉都阻止快进。
4. 不执行隐式 stash、rebase、冲突合并或丢弃修改。

## Push

1. 需要上传的修改必须先完成 commit。明确展示本次推送的仓库、远端目标分支和待推送提交；仍未提交的文件保留在本地，并提示其不会上传。
2. 先 fetch，再按最新状态判断是否允许向该目标分支推送。存在远端独有提交时提示“远端有更新，不允许 push”，提供用户主动选择的“新建分支并推送”入口；本次不自动更新文件或创建分支。
3. 使用普通 push，显式限定目标分支，不批量推送其他分支或标签。
4. fetch 与 push 之间远端仍可能发生变化。发生非快进拒绝时重新 fetch 并重新判断，不尝试强推。
5. 遇到分支保护、权限不足或认证失败时保留本地提交并展示原因，不把它们统称为代码冲突。
6. 网络中断导致结果不确定时，先核对远端是否已包含本次提交，再决定是否重试。

### Push 进度展示

点击 push 后打开统一进度弹窗，按真实执行顺序展示以下步骤：

1. 以逐字输入效果显示 `git fetch origin`，执行中显示循环省略号与已用时间，完成后标记结果。
2. 展示“检查本地与远端提交状态”。检查通过才进入 push；发现远端有更新时停止等待动画，提示“远端有更新，不允许 push”，将 push 标记为未执行，并提供“新建分支并推送”和关闭入口。
3. 允许推送时，以逐字输入效果展示包含实际目标分支的等价 push 命令，等待真实结果后显示成功或失败。

用户选择“新建分支并推送”后，在同一弹窗中继续展示创建分支及推送新分支的执行步骤。动画只负责呈现任务状态；重新打开界面不能重跑任务，失败后的重试仍需重新执行必要的状态检查。视觉及交互规则见 [README.md](README.md#耗时操作弹窗与动画)。

## 临时分支

从当前本地 `HEAD` 创建临时分支，例如 `agit-tmp/main-20261107-153000-a1b2`。名称需要合法且与已有本地、远端分支不冲突；原分支名称包含 `/` 时需转换为可用于该命名结构的形式。

创建前必须完成需要上传内容的 commit，并结束外部编辑。保留原分支引用，基于当前本地旧代码节点及其开发 commit 创建并切换到新分支，无需 cherry-pick；未勾选提交的文件变化保留在工作区，不隐式提交。随后将临时分支推送到 `origin` 的同名新分支，成功后配置对应的远端跟踪关系。不继承原分支的 push 目标，不修改原远端分支。

临时分支只负责把本地成果送到远端，不表示已包含远端新代码，也不表示冲突已经解决。失败时保留当前分支、提交及文件，允许检查状态后重试，不自动删除临时分支。

推送后保留新分支作为当前分支，后续检查以其同名远端分支为目标。原分支的远端更新仍未整合，后续合并交由电脑或 GitHub 处理。

## 异常与任务边界

- 同一仓库的 Git 写操作和文件回写串行执行，防止 commit、更新或切换分支交错修改目录；切换抽屉项目后，旧任务结果仍归属原项目。
- 刷新优先复用 Job 取消、结构化等待和项目身份校验；不额外引入无具体竞态依据的版本计数。
- 上游缺失、远端目标分支已删除、没有共同历史或仓库处于未完成 merge/rebase 状态时，停止自动同步并给出具体原因，不猜测替代分支。
- Git 执行引擎在实施前单独验证 Android 兼容性、HTTPS Token 认证、取消行为及上述提交关系判断，不预先承诺手机环境存在系统 `git`。

Git 语义依据：[git-fetch](https://git-scm.com/docs/git-fetch)、[git-push](https://git-scm.com/docs/git-push)。
